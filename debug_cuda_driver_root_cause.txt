CONFIRMED CUDA STARTUP ROOT CAUSE — 25 October 2026

This is not a PyTorch-version mismatch. Lora's system libcuda binary differs from the
working same-release driver and contains zeroed executable code at the crash site.

Installed environment on both nodes:
Python3.10.17, torch2.3.1+cu121, torchvision0.18.1, Triton2.3.1, Accelerate1.1.1,
timm1.0.11, CUDA runtime12.1.105, cuBLAS12.1.3.1, cuDNN8.9.2.26, NCCL2.20.5.
NumPy2.2.6 differs from requirements-uv.txt's1.26.4 pin, but NumPy is unnecessary to
reproduce this native C driver failure and is not the cause established here.
Both nodes report NVIDIA kernel driver595.91.07 and the same source version.

Failing system library:
/usr/lib/x86_64-linux-gnu/libcuda.so.595.91.07 on lora
Size91505672 bytes; ELF build IDf5196a66c4b4c4122e3824c3a5aa89734c258f7d.
SHA25616c7bed82c51b3d358e5dc0ceda691092860df913ceef193196511fb0449868d

Working same-release library on deepmedic2:
Same size and build ID.
SHA2564839b5da17cd8f58a8e9c57e97c9b61f3c41be7934479f48afc983416b2492c3

Exactly31947 bytes differ, all within file offsets0x2b7000..0x2bffff (36KiB range).
The crash-site bytes around0x2b8d30 are zero in Lora's copy and valid machine instructions
in the working copy. Lora has31947 additional zero bytes in total.
The checked libnvidia-ml, libnvidia-ptxjitcompiler, and libnvidia-nvvm hashes match across
nodes, so this is specifically a libcuda content discrepancy, not just version-label drift.

Native proof:
A standalone C program calls dlopen(libcuda.so.1), cuDriverGetVersion, cuInit(0).
It imports neither Python nor Torch and does not use the wheel's CUDA runtime.
cuDriverGetVersion succeeds (13020); cuInit segfaults at libcuda offset0x2b8d30 on Lora.
The same native program succeeds on deepmedic2. JIT-preload0/1 settings do not help.
This rules out Python, NumPy, model code, compilation, and NCCL as required causes.

Controlled successful workaround on Lora (job82806):
Copied the working library into user-owned diagnostic storage; verified its SHA256.
Selected it only for the test process using LD_LIBRARY_PATH; left all system files alone.
Native cuInit and cuDeviceGetCount succeed.
The SAME torch2.3.1+cu121 environment reports CUDA available, allocates on NVIDIA L40S,
and computes a32-element dot product with result32.0. /proc/self/maps confirms the
reference library was loaded. Native and Torch subprocesses both exit0.
